# Known issues and validation status

Updated 2026-11-13 for the CPU physics default and saved drive-graph cleanup. Runtime observations below come from the earlier named sessions; inspect the current Kit and ROS processes before treating them as live state.

## Confirmed and actionable

- **OAK-D depth and CameraInfo stream desynchronization:** Downstream ROS 2 perception nodes (such as `PointCloudXyzNode` from `depth_image_proc`) report synchronization failure:
  ```text
  [WARN] [PointCloudXyzNode]: [image_transport] Topics '/oak_d/depth' and '/camera_info' do not appear to be synchronized. In the last 10s:
      Image messages received: 0
      CameraInfo messages received: 24
      Synchronized pairs: 0
  ```
  This is caused by two compounding factors:
  1. *Topic namespace mismatch:* In `/ActionGraph`, one camera info helper was authored with relative topic `oak_d/camera_info` while depth publishes to `/oak_d/depth`. Default ROS 2 `depth_image_proc` launch configurations listen for `/camera_info` at the root namespace unless explicitly remapped.
  2. *Render product frame drops under GPU load:* While the tick-driven `ROS2CameraInfoHelper` continues publishing at ~2.4 Hz (24 messages per 10s), the GPU render product drops depth frames down to 0 under heavy PhysX/viewport load. Furthermore, if `image_transport` uses exact synchronization without shared simulation clock (`/clock`), minor timestamp drift causes all pairs to be rejected.
  *Remediation:* Explicitly remap subscription topics (`-r image_rect:=/oak_d/depth -r camera_info:=/oak_d/camera_info`), enable approximate synchronization (`approx_sync:=true`), and run `py agentic/sitl_harness.py --task camera` to audit render product resolution and publishing state.
- **Canonical stage unpromoted vehicle mass (mass = 0):** `/jackal/base_link` in `scenes/CAMERASYNCSSMOETIMES.usd` authors `physics:mass = 0`. The working 55 kg candidate scene (`CAMERASYNCSSMOETIMES_55KG_CANDIDATE.usd`) correctly authors ~53.09 kg base mass plus four 0.477 kg wheels, but this has not yet been promoted to canonical. PhysX infers mass from collision geometries when mass is 0, which leads to unpredictable terrain contact and suspension response. This is verified automatically via `py agentic/sitl_harness.py --task onboarding`.
- **Full GUI remains below the 60 FPS driving target.** GPU dynamics against the detailed terrain caused the original roughly 16 FPS run. CPU physics, now the scene and launch default, plus a 10 Hz OAK setting and one drive graph bring powered headless sand to roughly 63–69 FPS, but full-GUI Kit measured about 40–45 FPS while playing with OAK enabled. Tracy showed the large camera-on/off gap includes a Play-time switch to fast timeline mode, which triples physics/graph updates per displayed frame. With scheduling matched, enabling OAK adds about 1.1–2.3 ms/frame. A camera-on, forced realtime trial drove, formed a rut, delivered RGB/depth/lidar, and measured 57.0 FPS. `-NoOak` keeps driving, sand, lidar, TF, and clock active for fast teleop while omitting OAK image/CameraInfo streams; neither mode consistently satisfies the 60 FPS target. See `docs/performance-analysis.md`.
- **GUI timeline settings need a coherent-clock check.** The saved stage uses 24 time codes/s while the GUI timeline targets 60 FPS. With OAK active, Kit switched to fast playback and a 72 Hz loop limit at Play; the resulting simulation advanced faster than wall time. Forcing fast mode off raised the camera-on GUI result to about 57–58 FPS and preserved powered movement and sensor delivery in one trial. Validate physics time, wall time, `/clock`, image headers, and controller response together before making a persistent timing change. See `docs/performance-analysis.md`.
- **Lidar rays and points were hidden in the viewport.** `/jackal/base_link/laser/Lidar` is present and enabled, but the shared Jackal USD had `drawLines = false` and `drawPoints = false`. Both are now `true` in `assets/robots/jackal/ros2_jackal_PhysX_vlp16.usd`. The canonical and 55 kg candidate scenes inherit the corrected values. Reload the open stage after saving any unrelated unsaved edits to see the change; the current in-memory stage was not modified. This display setting is separate from `/scan` publication, which passed below.
- **The old stop script could stop teleop in another container.** `cometbot_dev` uses the host PID namespace, so its former `docker exec ... pkill` commands also matched processes in `aiaa_rover_dev`. `scripts/windows/stop_rover.ps1` now selects PIDs from `docker top` for the named container before signaling them. The intended Joy and teleop nodes were restarted and the legacy control nodes were stopped; both containers remain running.

A direct-wheel trial confirmed visible tile heights matched the rut field and Stop restored zero depth. Image content, camera-info calibration values, and physical mount calibration have not been measured. These are requirements only if the camera feed is part of the current simulation goal. Physical calibration requires a real camera reference.

## Previously listed items that are not current blockers

- **Sand full-mesh update regression:** the previous live write to 650,000 visual vertices stopped powered travel and reduced camera delivery. The sand scene now renders and collides with the same small tiles. Headless powered travel and sensor delivery passed under CPU and GPU physics; GUI handling and soil calibration remain open above.
- **Controller path and cross-host DDS:** in a tested 55 kg candidate session, WSL saw Isaac `/cmd_vel` subscribers and the user confirmed rover motion from the controller. A later launcher run with an already-running Kit process saw zero Isaac subscribers. The difference depends on the active Kit stage and ROS environment; do not infer a persistent firewall problem from either snapshot.
- **ROS sensor delivery:** `/scan`, `/tf`, `/oak_d/rgb/image_raw`, `/oak_d/depth`, and `/oak_d/rgb/camera_info` are advertised in WSL. One actual laser scan, RGB frame, depth frame, camera-info message, and TF message were received. Message content and sustained rates were not evaluated.
- **PoseTree warnings:** an earlier Isaac Sim log repeatedly reported `target getObjectType eInvalid` for `/jackal/base_link/laser` and camera frames. A subsequent `/tf` message includes `laser` and those camera frames, so the warning is not presently evidence of missing TF. It also does not explain the hidden lidar rays and points.
- **Docker input access:** `aiaa_rover_dev` can open both `/dev/input/js0` and `/dev/input/event0`; Joy and teleop are running. The older stale bind-mount issue was repaired.
- **Legacy container:** `cometbot_dev` is separate legacy work. Its mere presence is not a rover issue; check its current Joy/teleop processes before starting the new stack to avoid duplicates.
- **Wall normal map:** the stale BlackPaint UI default was already corrected to an existing project texture.
- **Wheel-controller limits:** the numeric limits look stage-scaled, but the user reports normal controller response. Do not retune them on the basis of their raw values alone.
- **USDC crate warnings:** several older referenced assets emit 0.7.0 deprecation warnings in standalone `usd-core`, but both scenes compose and render in Isaac Sim 6.1. This is a future format-maintenance concern, not an observed runtime failure.
- **Automatic node migration:** Isaac Sim 6.1 migrates old graph node types in memory and marks the stage unsaved. The saved graphs pass structural checks. Do not save the open stage solely to clear a migration marker; review any intended stage changes first.
